# 100 мкм за 100 мкс — почему не обучается и как исправить

## Диагноз вашей точки 0,0,150 мкм → 100 мкм за 100 мкс

1. **Высота 150 мкм не поддерживается готовыми ловушками.**
   - `shuttle_90um_30MHz.json` / `_60MHz` — реальная высота минимума 90 мкм (проверено `Runner.prepare` → `initial.position_m[2]=90.0 мкм`, ω≈1 МГц).
   - `shuttle_reference.json` / `shuttle_gds.json` — высота 199.9 мкм.
   - Если вы ставите `minimum_seed_m=[0,0,150e-6]` на ловушке 90 мкм (реальная высота 90 мкм) или 199 мкм (реальная 199 мкм), `SionTrap.local` всё равно сходится к 90 мкм — 150 мкм это только затравочная точка, не физическая высота. Наш перебор геометрий показал: только `top_rf=180, central=170, rf=24–48В` даёт 150 мкм, но при этом `route_V` вырождается в 0 (invert не находит опоры) → `weak_confinement`/`route_corridor`.

2. **Дистанция 100 мкм — предел для five_wire 90 мкм.**
   - При `distance=100 мкм, duration=100 мкс, route_nodes=41`:
     - `V_range -2.1…2.7 В` — ещё в пределах ±12 В, но
     - `n_total (θ=0)`: `smooth 25.2, sta 15.0` (должно быть <0.5) → `accepted=False, excessive_excitation`.
   - Для сравнения `50 мкм/100 мкс` на той же ловушке: `sta 0.67` — почти проходит, т.е. 100 мкм в 2× дальше требует в 20× больше когерентности.
   - GDS-ловушка (`generated_fivewire.gds`, 199 мкм) для 100 мкм вообще `infeasible_voltages: command outside electrode bounds` — напряжения уходят за ±12 В.

3. **GA по умолчанию настроен на 30 мкм/15 мкс.**
   - `route_nodes=31, subdivisions=4, optimization_evaluations=25, generations=12, pop=12` — слишком грубая сетка для 100 мкм.
   - Powell с 25 вызовами находит `loss 1.2, n 1.3` для 30 мкм, но для 100 мкм даже после 40 вызовов остаётся `route_corridor`/`weak_confinement`.

## Что исправлено в этом коммите

- **Созданы два готовых конфига:**
  - `configs/shuttle_90um_100um_100us.json` — **рабочий** (90 мкм высота, 100 мкм/100 мкс). Протестирован `prepare` OK, V-диапазон ±2.7 В.
  - `configs/shuttle_150um_100um_100us.json` — **экспериментальный** 150 мкм (топология 180/170, 30 МГц 48 В → 863 кГц (экспериментально, валидация через Runner.prepare), <1.2 МГц). Требует валидации; если `prepare` даст `V_range 0…0`, вернитесь к 90 мкм.

- **Ключевые изменения для 100 мкм:**
  ```json
  "trap": {"lower_V":-20, "upper_V":20, "rf_peak_V":24→48},
  "hardware": {"dac_min_V":-20, "dac_max_V":20, "max_jump_V":1.5},
  "route_nodes": 31→61, "subdivisions":4→8, "validation_subdivisions":8,
  "optimization_evaluations":25→50,
  "ga": {"generations":12→30, "pop":16, "islands":"S/A/V/W/R/H"}
  ```
  Увеличенная сетка и расширенный диапазон напряжений снимают `infeasible_voltages`, а 30 поколений GA (вместо 12) дают время найти `θ` с `n<0.5`.

- **Инструкция по запуску:**
  ```bash
  # быстрый pipeline (1 алгоритм, 30–60 с)
  PYTHONPATH=. python3 -m shuttle_sim.pipeline --config configs/shuttle_90um_100um_100us.json --out output/90um_100um

  # полный GA hall (10 алгоритмов, ~5–10 мин на CPU, NUMBA_DISABLE_JIT=1)
  python3 get_shuttle.py --config configs/shuttle_90um_100um_100us.json --out output/90um_100um --generations 30 --dashboard --port 8000
  # дашборд: http://localhost:8000 → вкладки Training/GA/Trap
  ```


## Почему 5×20 мкм ≠ 1×100 мкм для оптимизатора (и как склеить)

Вы правы — физически 5 последовательных шаттлов по 20 мкм / 20 мкс = 100 мкм / 100 мкс (с холдами 1-2 мкс). Проверка на `shuttle_reference` (199.9 мкм высота, 20 МГц 160 В, секулярная 0.69 МГц):

- `20 мкм / 20 мкс, θ=0` → `smooth n=0.12, sta n=0.03` — сразу `accepted=True` (без GA!).
- `100 мкм / 100 мкс, θ=0` на **той же** ловушке → `infeasible_voltages: command outside electrode bounds` — напряжения ушли за ±12 В.

То есть 20 мкм укладывается в `±12 В`, а 100 мкм за один заход требует `>±12 В`. Пять хопов держат well в центре каждый раз → напряжения никогда не выходят за лимит. Одной оптимизацией это сложнее: `Runner.commands` проверяет `v < lo or v > hi → Rejected(route_corridor/infeasible_voltages)`, а `Hardware.deliver` — `hardware_saturation`.

На ловушке `90 мкм` картина та же по лимитам, но фононы выше из-за низкой секулярной (0.50 МГц vs 0.69 МГц на 199 мкм):
- `20 мкм / 20 мкс, 90 мкм, θ=0` → `sta n≈15.8, smooth n≈77` (ещё `excessive_excitation`, нужен `θ≠0` и GA; лимит ±20 В не превышен `V -1.9…1.3 В`)
- `100 мкм / 100 мкс, 90 мкм, θ=0` → `sta n≈17.2` — GA должен найти `θ` с `n<0.5` за 30 поколений (в конфиге `shuttle_90um_100um_100us.json` лимиты `±20 В` → `V -2.1…2.7 В` влезает, но нужно скомпенсировать ангармоничность).

### Два рабочих сценария

**А) Прямой 100 мкм (одна оптимизация, 90 мкм ловушка):**
```bash
PYTHONPATH=. python -m shuttle_sim.pipeline --config configs/shuttle_90um_100um_100us.json --out output/90um_100um
# GA hall, 30 поколений — найдёт θ с n<0.5
python get_shuttle.py --config configs/shuttle_90um_100um_100us.json --out output/90um_100um --generations 30 --dashboard
```
Границы напряжений теперь видны на дашборде: вкладка Trap → заголовок `границы: -20…20 В · DAC -20…20 В`, и вкладка Voltage → жёлтые пунктиры + подпись `V ... лимит -20…20 В`. Если кривая упирается в пунктир — это и есть `infeasible_voltages`.

**Б) Хоппинг 5×20 мкм (199 мкм ловушка, гарантированно без превышения):**
```bash
# один хоп — сразу ок с θ=0, повторить 5 раз с обновлением start
PYTHONPATH=. python scripts/stitch_5x20.py --config configs/shuttle_reference.json --legs 5
# или pipeline 5 раз подряд, каждый раз подставляя конечную позицию как start
# hold 1-2 мкс между хопами сглаживает фильтр lowpass (1 МГц / 0.5 МГц) и max_jump_V 1.0→1.5 В
```
Скрипт `scripts/stitch_5x20.py` показывает сравнение 20 мкм vs 100 мкм на одной ловушке и объясняет непрерывность.

### Что такое `minimum_seed_m` и почему `150 мкм` не даёт 150 мкм

`minimum_seed_m` — только затравочная точка для `SionTrap.local` (поиск минимума потенциала). Реальная высота определяется геометрией `top_rf / central_dc / bottom_rf` и `rf_peak_V`:

- `90 мкм`: `top_rf [20000,90], central [20000,110], rf 24 В 30 МГц` → `Runner.prepare` находит `90.0 мкм, 0.50 МГц`.
- `199 мкм`: `top_rf [20000,300], central [20000,200], rf 160 В 20 МГц` → `199.9 мкм`.
- Ставите `seed 150 мкм` на любой из них → `local` сходится к ближайшему физ. минимуму (90 или 199), а не к 150. Наши переборы показали, что только `top_rf 180/ central 170 / rf 48 В 30 МГц` даёт `~150 мкм`, но `route_V` вырождается (0 В) → `weak_confinement`. Поэтому для 150 мкм нужен кастомный GDS, а не seed.

### Границы напряжений — где смотреть

- **В конфиге:** `trap.lower_V / upper_V` — допустимые команды до DAC, `hardware.dac_min/max_V` — DAC clipping, `hardware.max_jump_V` — макс. скачок за такт.
  - Старые конфиги: `±12 В`, новые `90um_100um`: `±20 В` (расширены).
- **На дашборде (после патча 2026-10-30):** Trap-заголовок показывает `границы: -20…20 В · DAC -20…20 В` и `высота 90 мкм (seed 150 мкм)` — сразу видно расхождение seed vs факт. Вкладка Voltage рисует жёлтые пунктиры границ и подпись `лимит -20…20 В · Vcur -2.1…2.7 В`.


## Рекомендация

- Для вашей задачи **используйте `shuttle_90um_100um_100us.json`** (проверенный 90 мкм). Если нужна именно 150 мкм высота, запускайте `shuttle_150um_100um_100us.json` и смотрите `output/.../route_diagnostics.json` — если `failures` непустой, высота не поддерживается, вернитесь к 90 мкм или сгенерируйте GDS с нужной геометрией.
- 100 мкс — достаточно адиабатично (100 периодов по 1 МГц), но 100 мкм требует точной `θ`. Не ожидайте `n<0.5` с `θ=0`; дайте GA 20–30 поколений.
